# release

**发版**

## Problem Statement

EchoPad 目前只能在维护者自己的电脑上手动打包：电脑端在本机签名、打包，手机端用 Android Studio 直接装到手机上。仓库还没有远程地址，也没有固定的发版流程；两端各有一个互不相干的版本号（电脑端 0.1.0，手机端 1.0）。用户拿不到安装包，维护者也没有一个固定的地方来写"这一版改了什么"。

## Solution

照 DevCube 的做法建立发版流程。维护者在本地用一条命令改好版本号、提交、打 `v*` 标签并推送；GitHub Actions 看到标签后先检查代码，再打出签名并公证过的 Mac 安装包和更新包、签名过的安卓安装包。全部成功后，一起发到公开仓库的同一个 GitHub Release。两端共用一个版本号，一个标签同时发布两端（ADR-0008）。更新日志手写在仓库根的 `CHANGELOG.md` 里：Release 正文只取这一版那段，整份日志随更新清单下发给两端（ADR-0011）。`main` 上持续跑两端的检查。应用内更新见 `docs/prd/in-app-update.md`。

## User Stories

1. 作为维护者，我希望在本地用一条命令升版本号、提交、打标签并推送，这样版本号和 Git 历史一一对应，由我确认之后才发。
2. 作为维护者，我希望两端的版本号只写在一个地方，这样两端的版本号不会对不上。
3. 作为维护者，我希望推一个 `v*` 标签就能自动发版，不用到网页上手动操作。
4. 作为维护者，我希望标签不在 `main` 上，或者标签和代码里的版本号对不上时，发版直接失败，这样不会从别的分支误发。
5. 作为维护者，我希望版本号带预发布后缀（如 `-beta`）时发版失败，这样在决定做 Beta 之前，不会误发出预发布版本。
6. 作为维护者，我希望 Mac 或安卓只要有一边打包失败就整个不发布，这样用户不会下到只有一半的版本。
7. 作为维护者，我希望缺少任何一项签名凭证时，在打包之前就明确失败，而不是发出没签名的包。
8. 作为维护者，我希望签名证书和各种钥匙只放在 GitHub Secrets 里，仓库里没有任何私钥。
9. 作为 Mac 用户，我希望下载到的安装包已经签名并经过苹果公证，这样打开时不会被系统拦住。
10. 作为 Mac 用户，我希望每个版本的签名都一样，这样更新之后不用重新授权辅助功能。
11. 作为安卓用户，我希望能在 GitHub Release 上下载到安装包，这样不经过应用商店也能装上。
12. 作为安卓用户，我希望每个版本都用同一个签名，这样新版本能直接装在旧版本上面，配对不会丢。
13. 作为用户，我希望在同一个 Release 里找到两端的安装包，这样在一个地方就能下全。
14. 作为用户，我希望 Release 正文就是这一版的更新日志，没写就留空，这样从网页下载时也知道改了什么。
15. 作为维护者，我希望在仓库里一个固定的文件里手写更新日志，这样日志由人来写，而不是从提交记录里拼出来。
16. 作为维护者，我希望某一版不写日志也照样能发，这样只有内部改动的版本不用硬凑内容。
17. 作为维护者，我只说一句"写更新日志"，就能按固定的写法一次写好这一版的日志，连版本号一起定好，这样日志简洁一致，不用再逐条调整。
18. 作为维护者，我希望漏写的日志能在下一版发布前补上，这样从更早版本升上来的用户也能看到。
19. 作为维护者，我希望每次推到 `main` 都在 CI 上跑一遍两端的检查和测试，这样能尽早发现问题。

## Implementation Decisions

- **仓库**：公开的 GitHub 仓库，安装包和更新清单都发在它的 Release 上；用户下载和应用检查更新都不需要任何凭证（ADR-0009）。
- **版本号（ADR-0008）**：两端共用一个 SemVer 版本号，只接受 `X.Y.Z`，不带预发布后缀。版本号只写在仓库根的 `package.json` 一处：`tauri.conf.json` 指向它，`Cargo.toml` 不写版本号，手机端构建时从它读取版本名。还没发版时版本号是 `0.0.0`。维护者在仓库根运行 `npm run release`：先拉取远端，再用 bumpp（经 npx 运行，仓库根不装依赖）改好版本号后提交、打 `vX.Y.Z` 标签并推送；工作区有未提交的改动时拒绝执行，避免漏提交的更新日志没跟上这一版（同 GodotStarter）。安卓的 `versionCode` 由版本号算出（`X × 10000 + Y × 100 + Z + 1`，加 1 是因为 `versionCode` 必须是正整数），因此次版本号和补丁号都不能超过 99，超过时手机端构建直接失败。
- **触发与门禁**：只有推 `v*` 标签才会发版。检查 job 先确认三件事：标签所在的提交在 `main` 上、标签和各处的版本号一致、版本号不带预发布后缀；然后跑两端的全部检查和测试。检查和打包同时进行，发布 job 要求两者都通过（同 DevCube）。
- **Mac 打包**：在 macOS runner 上打 arm64 的 `.dmg`（首次安装用）和 `.app.tar.gz`（更新包）。强制 Developer ID 签名并公证，凭证复用 DevCube 那一套（证书、证书密码、App Store Connect API Key），全部来自 GitHub Secrets；缺任何一项就在打包前失败，打包后再校验签名和公证票据。更新包另外用 Tauri 更新签名私钥签名，生成 `.sig`。
- **安卓打包**：在 Linux runner 上打 release APK，用发版签名文件签名；签名文件和密码来自 GitHub Secrets，缺任何一项就失败。只打一个不分 CPU 架构的通用 APK，不打 AAB。
- **文件名**：进 Release 的文件名一律不含空格。GitHub 会把文件名里的空格换成 `.`，导致下载地址对不上（DevCube ADR-0015）。
- **更新清单**：由发布 job 按 Tauri 官方的静态清单格式生成 `latest.json`，内容是版本号、更新日志，以及 Mac 更新包的下载地址和签名。手机端读的也是这一份（见 `docs/prd/in-app-update.md`）。不用 tauri-action（ADR-0011）。
- **发布编排**：打包 job 只上传构建产物。全部成功后，发布 job 用 GitHub CLI 一次性创建 Release，上传 Mac 安装包、Mac 更新包及签名、安卓 APK 和 `latest.json`，并标为最新版。不会出现缺文件的 Release。
- **更新日志（ADR-0011）**：仓库根的 `CHANGELOG.md`，格式照 Keep a Changelog：一级标题"更新日志"，每个版本一个二级标题 `[X.Y.Z]`（可以带日期），新版本在上，段内是无序列表。两端共用一份。发布 job 用成熟的 Markdown 解析器把它切成"版本 → 这一版正文"的列表，整份写进 `latest.json` 的 `notes`；Release 正文只取这一版那段，没写就留空。
- **写法规则**：维护者只说"写更新日志"时，照以下规则一次写完。版本号和每一条写不写都自己决定，不停下来确认，取舍在回复里说明；只改 `CHANGELOG.md`，不提交。
  - 范围：以上一个版本标签到当前代码的最终差异为准，只写用户能感知到的变化，不区分电脑端和手机端；同一个版本周期里加上又改掉的不写。
  - 版本号：有大功能时升次版本号，其余升补丁号；标题写 `[X.Y.Z]`，不写日期；这一版已有段落时，直接在原段落上改。
  - 条目：每条一句，以"新增 / 优化 / 修复"开头，句末不加句号，按新增、优化、修复的顺序排列；一个功能一条，同一个功能的多处改动合并成一条。
  - 粒度：只写到功能这一层，不展开具体做法；修复只写一个概括的问题现象，即"修复……的问题"。
  - 强调：每版最重要的一条整条加粗，最多一条；没有特别突出的就不加粗。
  - 细小改动：不影响功能的统一归为一条"优化交互体验"，放在优化类的最后；影响功能的，再小也单独写一条。
  - 内部改动（重构、依赖、构建、测试、CI、文档）不写；如果带来了用户能感知的变化，就按这个变化写。
  - 用词以 `CONTEXT.md` 为准，不照搬提交标题。
- **日常检查**：推到 `main` 时和每周定时运行。电脑端在 macOS runner 上跑类型检查、前端构建和 `cargo test`；手机端跑共享代码的测试和 debug 构建。不打发布包，也不签名。pnpm、Rust 编译产物和 Gradle 的缓存只由 `main` 写入，发版时只读（同 DevCube）。
- **Actions 安全**：用到的 Actions 都固定到完整的 commit SHA；workflow 默认只读，只有发布 job 有写权限。

## Testing Decisions

- 只测纯函数：更新日志的切段（识别版本标题、代码块里的井号不算标题、同一版本写了多段只取第一段、空文件）、取这一版那段（没写时为空）、发版前的标签校验（与版本号一致、不带后缀）、更新清单的内容。
- 不测 GitHub Actions 的编排、真实的签名和公证、打包结果。
- 维护者冒烟：首次发版后，在一台没装过的 Mac 上装 dmg、在手机上装 APK，确认都能正常打开；再发一版，确认两端都能在应用内更新（见 `docs/prd/in-app-update.md`）。

## Out of Scope

- Beta 和其他预发布版本。电脑端固定占用 47321 端口，还要单独授权辅助功能，正式版和 Beta 同时运行会抢端口，装两份的好处很小；需要时再加。
- Windows 和 Linux 电脑端（电脑端目前只支持 Mac），以及 Intel Mac 和通用二进制。
- iOS 手机端。
- 上架应用商店（Google Play、国内应用商店、Mac App Store）。
- 从提交记录自动生成更新日志；发版前强制检查日志有没有写。
- 自建下载站或 CDN。

## Further Notes

- 维护者需要准备好并存进 GitHub Secrets 的东西：Apple 证书和 API Key（复用 DevCube）、Tauri 更新签名私钥及密码、安卓发版签名文件及密码。后两样一旦丢了或换了，已经安装的用户就无法在应用内更新，必须另外离线备份。
- 只改了一端也会发一个新版本，另一端的用户同样会收到更新，这是共用版本号的代价（ADR-0008）。
- `CHANGELOG.md` 里的所有段落都会随更新清单发出去，为了本地预览临时加的段落，发版前要删掉。

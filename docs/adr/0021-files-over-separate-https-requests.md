# 发送文件走单独的 HTTPS 请求，由手机端发起

发送文件（docs/prd/send-files.md）要传可能几百 MB 的文件。现有连接是一条 WebSocket，触控、打字、语音都在上面按顺序收发；文件也走这条连接的话，一个大文件会挡在指针移动前面，传文件期间触控板卡住，切成小块穿插着发也只是减轻，而且要自己写分块、排队和流量控制。

所以文件在电脑端同一个端口上另发 HTTPS 请求，每个请求是一条新的 TLS 连接，和现有连接互不影响。连接仍然只由手机端发起（ADR-0015）：

- 手机端发文件：一批文件放进一个 `multipart/form-data` 上传请求，边读边传，电脑端边收边写磁盘，没有大小上限。
- 电脑端发文件：电脑端先通过现有连接把文件清单（名称、大小）告诉手机端，手机端再逐个发下载请求。清单里的每个文件只能下载一次，断线后整份清单作废，不用另外约定"下载完了"或"取消了"的消息。

请求用和现有连接一样的证书和指纹校验（ADR-0014），手机端在请求头里带上设备密钥（`Authorization: Bearer`），电脑端认得这把密钥才处理，局域网里的其他设备既传不进来，也拿不到文件。进度、取消和失败都在手机端处理：手机端是发起请求的一方，知道传了多少，取消就是中止请求。

KDE Connect 也是这个思路：控制消息走常驻连接，传文件另开连接。

## Alternatives Considered

- 在现有 WebSocket 上分块传：只有一条连接，但大文件和触控抢同一条通道，还要自己写分块、排队和流量控制。
- 另开一条专门传文件的 WebSocket：同样要自己写分块和确认，HTTP 的上传、下载和 `Content-Length` 本来就有这些。
- 像 KDE Connect 那样每次另开一个随机端口：多一个端口要过防火墙，电脑端还得把端口告诉手机端；用同一个端口上的不同路径就够了。
- 电脑端主动连手机端发文件：手机端不监听端口，后台和 iOS 上也做不到（ADR-0015）。

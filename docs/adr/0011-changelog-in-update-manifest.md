# 更新日志手写，切好段后整份写进更新清单

更新日志由维护者手写在仓库根的 `CHANGELOG.md` 里，两端共用一份（同 DevCube ADR-0035）。两端在确认更新前，都要列出当前版本之后、到新版本为止每一版的日志。发版流程用成熟的 Markdown 解析器把整份文件切成"版本 → 正文"的列表，以 JSON 写进 `latest.json` 的 `notes` 字段，随检查结果一起送到两端；两端只按版本号挑出需要的段落，不各自解析 Markdown。Release 正文只取这一版那段。

官方的本意是 `notes` 只放这一版的说明，我们放的是整份、切好段的日志。换来的好处是：日志和检查结果一起到，不用另发请求；Markdown 只在发版流程这一处解析，电脑端和手机端不用各写一份切段的逻辑。

`latest.json` 由发版流程按官方的静态清单格式自己生成，不用 tauri-action。原因有二：tauri-action 的 Release 正文和清单里的 `notes` 是同一个输入，做不到"Release 正文只放这一版、清单里放整份"；它还会在打包的 job 里直接创建 Release，和"两端都打包成功才发布"冲突。

## Alternatives Considered

- `notes` 放整份 Markdown，两端各自切段：和 DevCube 一样，但 Rust 和 Kotlin 里要各写一份切段的逻辑，还得保持一致。
- 把日志作为单独的 Release 附件：多一次请求，还要处理"查到了新版本、日志还没到"的状态。
- 从提交记录自动生成：日志是给用户看的，要人来写；提交标题里还混着内部改动。

## Consequences

- 更新清单会随着日志变长，每次检查都要下载一遍。等写到几百个版本、嫌它太大时，再考虑只带最近的若干版。
- `CHANGELOG.md` 里的所有段落都会随清单发出去。
